# Поисковая логика Country Search

## Контекст

Прочитай [AGENTS.md](../../../AGENTS.md), [прогресс](../../../docs/progress.md) и нужные разделы [ТЗ](../../../docs/TASK.md). Применяй [общие правила](../../rules/workflow.md), [архитектуру](../../rules/architecture.md) и [TDD и проверки](../../rules/testing.md). Для связи с UI прочитай контракт контроллера и затронутого компонента.

## Выполнение

1. Определи конкретный контракт или сбой и его владельца: API, преобразование, утилита или контроллер. Для bugfix воспроизведи проблему доступным способом и найди причину. Не переписывай сразу весь поиск.
2. Для новой обязательной логики сначала подготовь проверяемые сценарии и выполни тестовый этап TDD с сохранением порядка коммитов по правилам. Для существующего поведения добавь нужный регрессионный сценарий, если уместно.
3. Проверяй поведение на детерминированных данных. Для API нужны успешный ответ, 404, неуспешный статус и передача сигнала; для контроллера — немедленная отмена, очистка, различие таймаута и своей отмены, повтор последнего запроса. Выбирай сценарии по текущему изменению.
4. Реализуй минимальное изменение в нужном слое без DOM. При изменении модели проверь реальную схему ответа; используй подготовленные примеры для тестов без сети.
5. Если затронута конкурентность, проверь также промежуток ожидания debounce и запоздавшее завершение старого запроса. Отдельный тест гонки должен отличать настоящее abort от одного игнорирования ответа.
6. Запусти относящиеся к изменению тесты и доступные проверки типов, компиляции и линтера. При соединении с UI добавь проверку Network в браузере, не заменяя ею автоматические тесты.

## Результат

Опиши изменение контракта или причину исправления, результаты проверок и состояние этапов TDD. Обнови прогресс; при изменении алгоритма дополни корневой [DESIGN.md](../../../DESIGN.md) по фактическому коду. Кэш и история добавляются только в задаче на бонусы.
