# Архитектура Country Search

Обязательные технологии, выбранные инструменты и статус их настройки описаны в [стеке проекта](STACK.md).

## Статус и инструменты

`main.ts` соединяет API, контроллер поиска и интерфейс. Результаты поступают из countries.dev; подробности используют уже полученную страну без нового запроса. `createApp.ts` соединяет форму, карточки, статусы и диалог. При новом вводе старые результаты убираются, при отсутствии результатов показывается подписанный пример Японии. Стили разделены на токены, базовые правила, компоновку и компоненты. Сцена `flagScene.ts` изолирована в UI: получает страну, управляет текстурами и кадрами, освобождает ресурсы. Диалог передаёт внешнюю паузу через callback. Контроллер в `src/search/` управляет состояниями, отменой, задержкой и таймаутом.

TypeScript 6.0.3 установлен локально и закреплён в `package.json` и `package-lock.json`. Версия проверена по [npm registry](https://registry.npmjs.org/typescript/6.0.3) и выбрана с учётом поддержки typescript-eslint. Vitest, ESLint, Prettier, Husky, lint-staged и вспомогательные инструменты установлены в точных версиях из [стека](STACK.md); конфигурации, npm-скрипты и Git-хуки настроены. `typecheck` и сборка через `tsc` проверены; Vite используется только инфраструктурой тестов.

## Распределение ответственности

Бонусный слой `api/cachedSearch.ts` оборачивает API, хранит ограниченный TTL-кэш и объединяет transport для одинаковых запросов с независимой отменой потребителей. `search/searchHistory.ts` изолирует проверку и хранение истории. `main.ts` соединяет их с контроллером; кнопки истории создаются DOM-компонентом формы и передают выбранную строку обратно.

| Место             | Ответственность                                           |
| ----------------- | --------------------------------------------------------- |
| `index.html`      | Метаданные, CSS и подключение скомпилированного ES-модуля |
| `src/main.ts`     | Создание и соединение модулей приложения                  |
| `src/api/`        | HTTP-запросы, проверка статуса и передача сигнала отмены  |
| `src/models/`     | Типы ответа и модели страны, преобразование данных        |
| `src/search/`     | Состояние, жизненный цикл поиска, отмена и ошибки         |
| `src/utils/`      | Независимый debounce                                      |
| `src/ui/`         | Элементы страницы, события и отображение состояния        |
| `src/styles/`     | CSS                                                       |
| `tests/fixtures/` | Снимки ответов API для тестов                             |
| `DESIGN.md`       | Обоснование реализованных решений                         |

Реализованы `models/country.ts`, `models/demoCountries.ts`, компоненты `ui/` и адаптивные стили. Реализованы также models/mapCountryResponse.ts, api/searchCountries.ts, api/errors.ts и utils/debounce.ts; реализован также контроллер в src/search/. Модель `Country` описывает потребности UI отдельно от сырого контракта countries.dev. Фактические ответы и граница преобразования описаны в [fixtures](../tests/fixtures/README.md). Вход JSON остаётся `unknown` до проверки; HTTP 404 обрабатывается до разбора JSON, поскольку его тело — обычный текст. Обязательные функции реализуем после тестов.

## Связи между модулями

`main.ts` соединяет интерфейс и контроллер. UI передаёт текст и действия пользователя контроллеру. Контроллер использует API и debounce, передаёт изменения состояния интерфейсу. API получает данные и использует модель для их преобразования. Модели и утилиты не зависят от UI или контроллера.

Логика поиска не импортирует DOM-модули: её можно проверить без браузера. DOM доступен интерфейсу и точке входа. Контроллер отменяет активную работу сразу при новом вводе; debounce задерживает только следующий поиск.

Для начала достаточно состояний: начальное, загрузка, результаты, ничего не найдено, ошибка. Тип SearchState описывает idle/waiting/loading/empty/results/error; данные стран присутствуют только в results. Дополнительный глобальный менеджер состояния не нужен.

## Компиляция

`src/**/*.ts` компилируются в `dist/` с сохранением структуры. `include` выбирает исходники, а `exclude` отсекает `src/**/*.test.ts` и `src/**/*.spec.ts` из начального набора файлов. Исключённый файл всё ещё может попасть в программу через импорт; модули приложения не должны импортировать тесты. Это ограничение описано в [справке exclude](https://www.typescriptlang.org/tsconfig/#exclude).

Используем `strict`, дополнительные проверки индексации и необязательных свойств, а также `noEmitOnError`. `module` и `moduleResolution` равны `NodeNext`, в `package.json` задано `type: module`; результат — ES-модули. В относительных импортах TypeScript указываем расширение будущего JavaScript-файла: например, `./ui/createApp.js`. Компилятор разрешает такой путь в исходный `.ts`, сохраняя `.js` в результате; см. [разрешение модулей](https://www.typescriptlang.org/docs/handbook/modules/reference.html).

На этапе настройки (пункт 4 прежнего плана) конфигурация проверена через `tsc --showConfig` и Compiler API установленного TypeScript 6.0.3. Примеры в памяти подтвердили строгие ошибки типов, блокировку вывода при ошибках, `.js`-импорты и сохранение структуры вывода. Виртуальное дерево файлов проверено сопоставителем шаблонов компилятора: тесты исключаются и во вложенных папках. На этапе визуального каркаса добавлены реальные относительные импорты; они компилируются и загружаются в браузере без изменения конфигурации.

Настройки сверены с официальной документацией: [module](https://www.typescriptlang.org/tsconfig/module.html), [rootDir](https://www.typescriptlang.org/tsconfig/rootDir.html), [strict](https://www.typescriptlang.org/tsconfig/strict.html).

В пункте 5 отдельно проверены реальные npm-команды: `build` запускает `tsc -p tsconfig.json` и записывает `dist/main.js`; `typecheck` добавляет `--noEmit` и сохраняет файлы `src/` и `dist/` без изменений. При контрольном запуске с отсутствующим конфигом обе команды возвращают TS5058 и код 1, выходные файлы не меняются. Скрипты передают ошибки компилятора без подавления, `noEmitOnError` остаётся включённым. Назначение параметров: [noEmit](https://www.typescriptlang.org/tsconfig/noEmit.html) и [noEmitOnError](https://www.typescriptlang.org/tsconfig/noEmitOnError.html).

CSS подключён напрямую из `src/styles/`. При публикации без отдельного упаковщика нужно разместить `index.html`, скомпилированный `dist/` и `src/styles/`, сохранив относительные пути. Содержимого одного `dist/` недостаточно.

Для локальной разработки `npm start` выполняет успешную сборку перед запуском `http-server . -a 127.0.0.1 -p 8080 -c-1`. Корень проекта раздаётся по HTTP с отключённым кэшем, сохраняя пути JS и CSS. Во втором терминале `npm run dev` запускает `tsc -p tsconfig.json --watch --preserveWatchOutput`: изменения TypeScript перекомпилируются в `dist/`, CSS доступен напрямую; страницу обновляем вручную. Подробный порядок запуска и остановки — в [README](../README.md). Настройки основаны на документации установленного http-server 14.1.1 и [режима наблюдения TypeScript](https://www.typescriptlang.org/docs/handbook/configuring-watch.html).

## Порядок реализации

Проверки инструментов отделены от сборки приложения: `vitest.config.ts` задаёт тесты `src/**/*.test.ts` в Node, `eslint.config.js` проверяет JS/TS, Prettier отвечает за форматирование. `npm test` запускает 68 тестов обязательных модулей, жизненного цикла контроллера и отдельной гонки запросов. Настройка passWithNoTests сохранена с первоначального этапа. `.husky/pre-commit` вызывает только lint-staged для staged-файлов, `.husky/pre-push` — `npm test`. `prepare` подключает локальные обёртки Husky; `.gitattributes` сохраняет LF в shell-хуках. Подробности команд и проверки хуков — в [README](../README.md).

1. Установить и проверить согласованные инструменты; настроить проверки и Git-хуки.
2. Собрать UI и все его состояния на демонстрационных данных.
3. Для обязательной логики повторять: падающие тесты → отдельный коммит → реализация → зелёные тесты → отдельный коммит.
4. Гонка запросов отдельно проверена моками с инверсией ответов и настоящей реакцией на отмену; следующий шаг — соединить контроллер с UI.
5. Дополнить `DESIGN.md`, проверить деплой и оформить сдачу.

Историю TDD нужно начать в Git до реализации логики. Базовая main с одним `.gitignore` опубликована в origin, каркас приложения сохранён отдельным коммитом в локальной ветке `country-search`. Инструменты, UI и документацию следует сохранять отдельно от обязательных пар тесты/реализация.
